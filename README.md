# Delivery Service

Микросервис службы международной доставки: принимает посылки, хранит их
в разрезе пользовательских сессий, периодически рассчитывает стоимость
доставки в рублях по актуальному курсу ЦБ и отвечает на вопросы о правилах
доставки с помощью RAG-помощника.

## Стек

- **FastAPI** + **Pydantic** - HTTP API и валидация
- **SQLAlchemy 2** (async) + **psycopg 3** + **PostgreSQL** — хранение
- **Alembic** - миграции схемы и справочных данных
- **Redis** - кеш курса доллара
- **httpx** - клиент к API курсов ЦБ
- **APScheduler** — периодический расчёт стоимости
- **LangChain** (core, text-splitters, qdrant, groq) — пайплайн RAG
- **Qdrant** — векторная база знаний
- **fastembed** — локальная модель эмбеддингов (ONNX, без PyTorch)
- **Groq API** — LLM для генерации ответов
- **loguru** - логирование (текст или JSON)
- **uv**, **docker**, **docker compose**, **ruff**, **mypy** (strict), **pytest**, **pre-commit**, **poethepoet** - инструменты разработки и развёртывания

## Быстрый старт


```bash
cp .env.example .env   # для RAG-помощника впишите GROQ_API_KEY
docker compose up --build
```

Compose поднимет PostgreSQL, Redis и Qdrant, применит миграции и загрузит
базу знаний отдельными одноразовыми сервисами `migrations` и `knowledge-base`
и запустит приложение.

Первая сборка образа скачивает модель эмбеддингов (~220 МБ) с Hugging Face.
Без `GROQ_API_KEY` сервис работает, но эндпоинт поддержки отвечает 503.

- Swagger UI: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc

## API

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/packages` | Зарегистрировать посылку, вернуть её id |
| `GET` | `/packages` | Список своих посылок: пагинация (`limit`, `offset`), фильтры (`type_id`, `has_delivery_cost`) |
| `GET` | `/packages/{package_id}` | Данные одной своей посылки |
| `GET` | `/package-types` | Справочник типов посылок |
| `GET` | `/health` | Проверка живости для healthcheck Compose |
| `POST` | `/packages/fill-missing-costs` | Запустить расчёт стоимости вне расписания (только при `APP_DEBUG=true`) |
| `PUT` | `/packages/{package_id}/company` | Закрепить посылку за компанией. `company_id` передаётся в теле запроса. |
| `POST` | `/support/questions` | Задать вопрос службе поддержки (RAG): `{"question": "..."}` → ответ и разделы правил, на которых он основан |

Если стоимость доставки ещё не рассчитана, в поле `delivery_cost_rub`
возвращается строка `"Не рассчитано"`.

### Пользователи и сессии

Авторизации нет. При первом обращении сервис выдаёт cookie `session_id`
со случайным UUID; все посылки привязываются к нему. Разные браузеры
(или разные HTTP-клиенты) — разные пользователи.

Cookie выставляется с флагами `HttpOnly` и `SameSite=Lax`; флаг `Secure`
включается переменной `SESSION_COOKIE_SECURE` (нужен при работе по HTTPS).
Повреждённая cookie (не UUID) считается отсутствующей: сервис выдаёт новую
сессию, а не отвечает 422 на каждый запрос.

Чужая посылка по id возвращает **404, а не 403**: ответ не раскрывает,
существует ли посылка с таким id.

### Формат ошибок

Все ошибки возвращаются в одной форме:

```json
{
  "code": "package_not_found",
  "message": "Package with id = 999 not found",
  "details": null
}
```

| Код | HTTP | Когда |
|---|---|---|
| `package_not_found` | 404 | Посылки нет или она принадлежит другой сессии |
| `package_type_not_found` | 422 | При создании указан несуществующий `type_id` |
| `package_already_assigned` | 409 | Посылка взята компанией с другим `company_id` |
| `validation_error` | 422 | Тело или параметры запроса не прошли валидацию; подробности в `details` |
| `rate_unavailable` | 503 | Курс не удалось получить ни из кеша, ни из ЦБ |
| `support_not_configured` | 503 | Не задан `GROQ_API_KEY` |
| `knowledge_base_unavailable` | 503 | Qdrant недоступен или коллекция не загружена |
| `llm_unavailable` | 503 | Groq недоступен, ключ неверный или исчерпан лимит запросов |
| `api_using_error` | 404/405 | Неизвестный путь или метод |
| `internal_error` | 500 | Непредвиденная ошибка; подробности только в логах |

## Расчёт стоимости доставки

```
стоимость = (вес_кг * 0.5 + стоимость_содержимого_usd * 0.01) * курс_usd_rub
```

Стоимость **не считается в момент регистрации**. Регистрация только
сохраняет посылку, а фоновая задача раз в 5 минут одним `UPDATE`
проставляет стоимость всем посылкам, у которых её ещё нет.

Зачем так:

- регистрация не зависит от доступности внешнего API ЦБ;
- один запрос к ЦБ обслуживает все накопившиеся посылки;
- расчёт выполняется на стороне базы, без выгрузки посылок в приложение,
  поэтому одинаково работает и для десяти, и для миллиона строк.

Задача идемпотентна: она трогает только строки с `delivery_cost_rub IS NULL`,
поэтому повторный или параллельный запуск (плановый + ручной) не пересчитывает
уже обработанные посылки. Такие строки находит частичный индекс
`ix_packages_delivery_cost_pending`: в нём лежат только ещё не посчитанные
посылки, поэтому задача не сканирует всю таблицу.

Колонка стоимости (`Numeric(14, 2)`) вмещает результат для максимальных веса
и стоимости содержимого, которые допускает API, при курсе до ~950 000 ₽/$.
Иначе одна большая посылка вызывала бы переполнение и откатывала расчёт
для всех посылок разом.

### Курс доллара

1. Курс берётся из Redis (TTL задаётся `EXCHANGER_REFRESH_HOURS`).
2. Если в кеше пусто — запрашивается у ЦБ и кладётся в кеш.
3. Если Redis недоступен — это деградация, а не ошибка: курс берётся
   напрямую у ЦБ, в лог пишется предупреждение.
4. Если недоступны и кеш, и ЦБ — расчёт в этом цикле пропускается
   (посылки остаются «Не рассчитано») и будет повторён при следующем запуске.

Вместе со стоимостью в БД сохраняется курс, по которому она посчитана
(`exchange_rate`), чтобы итоговую сумму можно было объяснить.

## Служба поддержки (RAG)

База знаний — выдуманные правила доставки и таможни в
`knowledge_base/rules.md`. Используется RAG в два шага: на каждый вопрос
сначала поиск, потом генерация.

**Загрузка базы знаний** (сервис `knowledge-base`,
`python -m delivery_service.ingest_knowledge_base`):

1. Файл режется на куски: сначала по разделам `##`, чтобы кусок не смешивал
   темы, длинные разделы — дальше по абзацам и предложениям. Название раздела
   сохраняется в метаданных куска.
2. Каждый кусок векторизуется локальной мультиязычной моделью
   `paraphrase-multilingual-MiniLM-L12-v2` (вектор из 384 чисел).
3. Векторы вместе с текстом записываются в коллекцию Qdrant. Коллекция
   пересоздаётся при каждом запуске, поэтому правка файла правил применяется
   перезапуском сервиса без дублей.

**Ответ на вопрос** (`POST /support/questions`):

1. Вопрос векторизуется той же моделью, в Qdrant ищутся `KNOWLEDGE_BASE_TOP_K`
   ближайших кусков.
2. Куски с косинусным сходством ниже `KNOWLEDGE_BASE_MIN_SCORE` отбрасываются.
   Если не осталось ни одного, сервис сразу отвечает «нет ответа в правилах»
   и не тратит запрос к LLM.
3. Найденные куски и вопрос подставляются в промпт. Системная инструкция
   требует отвечать только по правилам, не выдумывать и отправлять к оператору,
   если ответа нет. Текст правил помечен как данные, а не инструкции
   (защита от инъекций промпта).
4. Промпт уходит в модель Groq (`temperature=0` для стабильных ответов),
   в ответе возвращаются текст и названия использованных разделов правил.

Модель эмбеддингов вшивается в Docker-образ при сборке, чтобы контейнеры
стартовали без скачивания.

## Разработка

```bash
uv sync                      # окружение с dev-зависимостями
uv run pre-commit install    # хуки: ruff, mypy при коммите; pytest при пуше

| `uv run poe typecheck` | Проверка mypy |
| `uv run poe lint-check` | Проверка ошибок линтинга |
| `uv run poe lint-fix` | Исправление ошибок линтинга |

| `uv run poe test-api` | Прогон api тестов |
| `uv run poe test-all` | Прогон всех тестов |

| `uv run poe check` | Линтер, форматирование, проверка типов и тесты |

Тесты в той же среде, что и прод-образ:

```

### Структура

```
src/delivery_service/
├── api/          # роутеры, pydantic-схемы, зависимости, обработчики ошибок
├── services/     # бизнес-логика: посылки, курс, расчёт стоимости, поддержка (RAG)
├── clients/      # клиент API курсов ЦБ, адаптер модели эмбеддингов
├── db/           # модели SQLAlchemy и сессия БД
├── config.py     # настройки из окружения
├── scheduler.py  # периодическая задача
├── ingest_knowledge_base.py  # загрузка базы знаний в Qdrant
└── main.py       # сборка приложения и жизненный цикл ресурсов
alembic/          # миграции (схема + справочник типов посылок)
knowledge_base/   # правила доставки для RAG-помощника
```

Слои зависят только «вниз»: роутеры вызывают сервисы, сервисы — клиентов
и БД. Сервисы не знают про HTTP и бросают доменные исключения, которые
в HTTP-ответы превращает слой `api`.

## Принятые решения и ограничения

- **«Не рассчитано» вместо `null`.** Требование ТЗ выполнено на уровне
  сериализации: в БД хранится `NULL`, строка подставляется только в ответе.
  Для машинных клиентов `null` был бы удобнее (строку приходится
  сравнивать, и любое её изменение ломает интеграцию).
- **Нулевая стоимость доставки допустима.** Формула не содержит базовой
  ставки, поэтому лёгкая посылка с нулевой стоимостью содержимого может
  дать сумму, округляющуюся до `0.00`.
- **Формат ответа ЦБ считается стабильным.** Ошибки сети, HTTP-статусы,
  не-JSON и отсутствие ключа обрабатываются; содержимое поля курса
  дополнительно не валидируется.
- **Сессия = cookie.** Потеря cookie означает потерю доступа к посылкам;
  это прямое следствие отсутствия авторизации по ТЗ.
- **Планировщик живёт в процессе приложения.** Для одной реплики этого
  достаточно. При масштабировании API планировщик нужно вынести в отдельный
  процесс (тот же образ, другая команда), иначе задача запустится в каждой
  реплике.
- **Миграции — отдельный сервис Compose.** Приложение стартует только после
  их успешного завершения. На Compose 5.3+ то же самое можно выразить через
  `pre_start` у сервиса `app`.
- **`/health` проверяет только живость процесса**, а не Postgres, Redis и Qdrant:
  перезапуск приложения не починит упавшую зависимость, а роуты, которым она
  нужна, и так отвечают своими ошибками. Compose перезапускает `app` при падении
  процесса (`restart: unless-stopped`); по статусу `unhealthy` сам Compose
  контейнер не перезапускает, это делает оркестратор (Kubernetes, Swarm).
- Значение **type_id** ограничено типом int. Значения выходящие за диапазон возвращают ошибку 500.
- Не удобно настроена работа с **Docker** в *dev*, *test* и *prod* средах.
- **RAG в два шага, а не агентный.** ТЗ описывает именно схему «найти →
  передать в LLM», и на один вопрос уходит ровно один запрос к модели.
  Агент с инструментами (поиск по правилам + API посылок) имеет смысл, если
  помощник должен отвечать и про конкретные посылки пользователя.
- **Поиск только по смыслу.** Маленькая модель плохо понимает редкие слова:
  на «Можно ли переслать пауэрбанк?» нужный раздел не попадает в выдачу,
  и помощник честно отправляет к оператору, хотя правило есть. Лечится
  гибридным поиском (векторы + поиск по словам; Qdrant и `langchain-qdrant`
  это поддерживают) или более крупной моделью эмбеддингов.
- **Порог сходства подобран вручную** на нескольких вопросах и привязан
  к модели эмбеддингов: при смене модели его нужно подбирать заново.
- **Нет ограничения частоты запросов к поддержке.** Защита сейчас только
  на стороне Groq: при исчерпании бесплатного лимита эндпоинт отвечает 503.
- **Groq доступен не из всех регионов.** Для запросов к нему есть отдельная
  настройка прокси `GROQ_PROXY_URL`, остальной трафик через неё не идёт.
- **База знаний пересоздаётся при каждом запуске Compose.** Пока идёт загрузка
  (секунды), коллекции нет. Без простоя это делается загрузкой в новую
  коллекцию и переключением алиаса Qdrant.
